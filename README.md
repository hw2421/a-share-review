## 空间龙头口径（一字板过滤）
**连续一字板无换手的连板股不统计为空间龙头**：当前连板段每一板都是"集合竞价封死（首次涨停时间 ≤09:26）且全天未开板"的一字板（买不进、无换手）时，该股不计入当日空间龙头、压制链与空间周期线；**空间高度改由换手股中的连板最高者承担**，一字板再高也不触发"突破"。被排除的个股在当日 note 中标注（如"一字连板不计空间:新华传媒10板"）。盘中"⟳ 刷新"实时数据同口径（recentPools 携带 ay 全程一字标志递推）。

## 题材梯队口径（空间情绪明细表 / 题材炒作 / 赚钱效应 / 连板梯队 同源）
> 旧实现：明细表用「当日题材块」算梯队，块不足 5 只被丢弃后前端**回看 6 个交易日**，于是出现 **「4 板龙头配 3-1 梯队」的错配**（2026-11-16 北纬科技 4 板显示 3-1）。现已彻底改为同一日池内重建：

- 明细表 `题材·梯队·阶段` **只显示当日梯队、当日阶段**，不再借历史日；同题材同色（与题材炒作图共用一张颜色表）
- 校验：`verify_space.py` 第 6 项（空间龙头板数落在自身题材当日梯队、每日 2 板以上连板股板数出现在其题材梯队）全期 1418 日通过；另做块×梯队审计：**3503 个题材块 0 不一致**，全部满足新门槛、块内个股全在当日涨停池

## 3. 赚钱效应
- **只显示「板块有三连板或以上个股、今日再次涨停」且「板块至少 3 只涨停」的题材**：当日真实涨停池里该题材最高连板 **≥3**（这些股今日确实涨停、且是连板晋级），**同时池内该题材真实涨停个股 ≥3 只**；不达标的交易日显示一行说明并列出当日已有梯队，不再看起来像缺数据
- **题材后展示当日题材阶段**：卡片题材名紧跟 **启动 / 加强 / 转弱 / 反复** 色标，与题材炒作页卡片的阶段**同一四分类算法**（数据层 `build_merged.py` 5.6.0 全期算出 `money[].stage`，前端刷新时用同算法兜底）；`verify_space.py` 第 10 项逐组复算比对，2941 组 0 不一致
- **板块日均涨幅只统计板块「2 连板及以上」个股**：取昨日涨停池内该题材 2 板以上的个股，用本地真实日K（不复权收盘价环比）算今日涨跌幅均值，**剔除首板跟风股**，卡片标注参与只数
- **卡片精炼**：每张卡只保留 **题材名 + 当日阶段 + 当日梯队 + 2板+日均涨幅**；龙头/中位股/首板跟风/逐股 chips/昨日涨停家数/旧「今均」等冗余数据全部删除，卡片更小、排版更密
- **点击梯队 → 浮层显示当日该题材梯队个股**：复用题材页梯队浮层（各板级横条 + 当日全部涨停个股、最高板红框标记），点个股名看日K
- 全期按**当日真实涨停池 + 本地日K**重算（`build_merged.py` 5.6.1），不再依赖复盘文章标注或估算行情；题材名与全站统一归一，无题材归属的"其他"分组不显示
- 按日期降序、**近1月 / 近3月 / 全年**范围切换，与题材炒作图一致

## 4. 连板梯队（第四个导航）
- **紧凑密集线格（表格式横竖分隔线）**：左侧板级列收窄至 40px（手机 34px），个股格 `minmax(104px,1fr)`（手机 92px）、内边距/字号同步压缩，**多个个股并排一行、不再一人占一大行**，整页高度大幅缩小；格子自带右/下边框形成连续横竖线；空白区域与格子同色，不会出现亮色断层

### 战法五「黑盒模式」的历史挖掘结论
以赚钱效应题材内的换手涨停股为候选池（挖掘时基于 695 个交易日 / 5043 笔历史快照样本；页面逐笔为全期扩展候选池、含收盘炸板股，笔数更多），按统一卖出规则回测后分组统计：

| 特征 | 最优分组 | 笔均 / 胜率 |
|---|---|---|
| 首次封板时间 | **≤10:00（早盘）** | +3.36% / 59.1%；尾盘≥14:00 仅 +0.51% / 41.3% |
| 成交量 | **缩量（量比 <1）** | +3.77% / 63.5%；量比≥3 仅 +1.37% |
| 市场阶段 | 突破 / 主升 | +3.24% / +3.16%（节点仅 +2.22%） |
| 题材阶段 | 反复 / 加强 / 启动 | +3.23% / +2.61% / +2.56%（转弱仅 +1.97%） |
| 板块涨停家数 | 5–6 只 | +3.06% / +2.88%（7 只以上反而 +2.38%） |

由此固化两个买入模式取并集：**A 早盘缩量接力**（首封≤10:00、量比<1、2–5 板、题材阶段非转弱）、**B 突破主升龙头**（板块最高板 3–6 板、板块涨停≥3 只、题材启动/加强、市场突破/主升）。挖掘样本上基准全体胜率 54.9% / 笔均 +2.59% / 盈亏比 1.80，A∪B 共 390 笔提升到胜率 65.4% / 笔均 +4.93% / 盈亏比 1.89。

**卖出逻辑（以赚钱效应为理论基础）**：赚钱效应本质是资金接力。对比三种卖出方案——固定「次日不连板尾盘卖」**+2.59% / 盈亏比 1.80**、「等题材赚钱效应整体消退才卖」+2.24% / 1.66、「题材阶段转弱即卖」+2.30% / 1.69——等待板块层面信号会滞后 1~2 天、每笔回吐约 0.3pct。因此**以个股层面的接力延续为持有依据**：个股次日仍封涨停（赚钱效应在该股上延续）就持仓，首个收盘未涨停日立即尾盘卖出，盘中跌幅 >7% 无条件止损。

- 卖出：统一卖出规则。

**战法二 · 凹凸曼（ultraman）**
- 买入：发现凹凸曼形态当日**不参与**；**买入当天市场阶段属于补涨、突破**。形态＝板块 3–5 板龙头涨停后炸板再回封、放出近 20 日最大成交量（`vol_is_max`），且板块有次高连板 2 板或以上。**次日该股高开**（`gap_open_up()`：开盘价 > 昨收）**且再度涨停**（封板或盘中触板炸板）才以涨停价打板买入；买点距买入当日空间压制 ≥2 板；买入当日炸板仍按涨停价模拟买入。
- 卖出：统一卖出规则。

**战法三 · 试错龙头（trialLead）**
- 买入：**买入的前一日市场为节点阶段**，今日预期为补涨、突破或主升（前一日为突破或主升则不参与，`m3_prev_skip`）。板块当日有赚钱效应（≥3 板个股再涨停且板块至少 3 只涨停），龙头 3 板以上，且板块有连板中位股（2 板+ 非龙头）今日连板或红盘，**或今日板块内有新的连板股**（`new_lb_stock()`：当日新晋级 2 板+）。买的是板块龙头本身，买点距买入当日空间压制 ≥2 板；收盘炸板龙头也按涨停价模拟买入。
- 卖出：统一卖出规则。

**战法四 · 补涨（fillUp）**
- 买入：**买入当天市场为突破、主升或补涨阶段**，龙头符合战法一/二/三之一；标的所属板块**昨日有赚钱效应**（3 板+ 连板龙头且板块内 5 个以上涨停，`prev_money_ok()`），但当日板块龙头一字涨停（无法买入），改买板块次高的换手连板股（非一字、2 板+）。次高股收盘炸板也按涨停价模拟买入。
- 卖出：统一卖出规则。

**战法五 · 黑盒模式（blackbox）**
- 买入：**融合空间突破、凹凸曼、试错龙头三种买点模式，符合任意一个则纳入模拟**——逐笔与机会池均为前三战法买点**并集**（同日同股去重、`mode` 标注来源战法），买卖点与全部门禁完全跟随来源战法。**已删除此前的「早盘缩量接力 / 突破主升龙头」A/B 挖掘模式**（`META.blackbox` 文案、`strategies.py` 选股逻辑、前端自省建议文案一并清理）。
- 卖出：以赚钱效应为理论基础（个股层面接力中断比板块整体效应消退更早更准），规则同统一卖出。

### 14.1 赚钱效应的操作定义（全局）

- **可买入**：收盘涨停且非一字（`is_oneword_up` / `e.yizi` 双判定）；涨停开盘后打开、盘中有换手仍算可买入。
- **次日赚钱**：次日**开盘价 > 买入涨停价**（隔夜正溢价，打板客竞价即可卖出获利）。不用「最高价」——涨停股次日几乎都会冲高（实测占比中位 90%，无区分度）；开盘溢价中位 64.3%，有区分度。
- **无未来函数**：T 日买入时只能观察 T-1 日「可买入涨停股」在 T 日是否赚钱，故示范一律取「前一交易日 → 买入当日」。
- **市场级**：T-1 日全市场可买入涨停股（样本 ≥5），在 T 日赚钱占比 **≥50%**。
- **板块级**：T-1 日所属板块至少 1 只可买入涨停股，在 T 日赚钱。
- **两级都过才参与**（用户拍板）。一字买不进属展示型机会（不参与模拟），豁免该门禁，保留「有买点但买不进」的自省价值。

## 数据传输与压缩（v13）
线上静态托管是 `python3 -m http.server`，**不做 gzip**（实测响应无 `Content-Encoding`），全期主包若明文写出会原样传输十余 MB，手机端首屏很慢。因此：
- `data.json` 用紧凑分隔符 `(",", ":")` 序列化，省掉默认 `", " / ": "` 产生的约 20% 纯空格；
- `data.js` 由 `datajs.py` 统一生成：自包含 `pako_inflate.umd.min.js`（32KB）+ zlib(9) 压缩串的 base64，浏览器走 `atob → pako.inflate → TextDecoder → JSON.parse` **同步解压**出 `window.REVIEW`（约 200ms），`index.html` 零改动、无额外请求；
- 所有会落盘主包的脚本（`build_merged.py`、`update_daily.py:write_alert`、`refresh_klines.py`）统一调用 `datajs.py`，避免日常维护时悄悄退化成明文；
- 回退：设 `NOCOMPRESS=1` 或缺少 `.pako_inflate.min.js` 时自动输出明文 `window.REVIEW=...`，功能完全等价，便于调试与人工核对；
- 实测（1418 日 v16 全期版本）：`data.json` **15.40 MB → `data.js` 3.21 MB（-79%）**，浏览器同步解压约 0.3~0.5s；453 日版本为 5.99 MB → 0.78 MB（-87%）。**v19 全期版本：`data.json` 16.57 MB → `data.js` 3.29 MB（-80%）**，线上 Playwright 首屏加载约 1.0s，新增 v19 板块助攻断言后线上真实环境全通过。全期经 Playwright 桌面/手机回归与线上真实环境解压验证，无控制台错误。

## 已知限制
- 赚钱效应全期按**当日真实涨停池 + 本地日K**重算；涨跌幅为新浪**不复权**日K收盘价环比，个股除权当日可能有小幅偏差
- 日K分片为按需加载的静态 JSON（单片约 2MB），首次点某只个股时会有一次网络读取；离线打开 `index.html` **必须连 `klines/` 目录一起拷贝**，否则点个股无日K（主包已不再内嵌日K）
- **2021-2025 年题材/连板数来自复盘长图 OCR 识别**（2021-2022 早期版式每天多张图，已实测可被 `parse_article` 正确解析出题材、个股、连板数与涨停时间），个别错字经归并修正，可能存在少量误差；股票代码错码经 `fetch_data.CODE_FIX` 映射后抓日K
- 交易复盘为**规则化回测**：v21 起凹凸曼在节点日不参与、试错龙头只在节点次日参与（节点例外仅对空间突破/补涨放行，详见第 13 节）；v19 起所有战法买入须有板块助攻（买入当日或前一交易日、板块内本股之外有 2 板+ 真实涨停连板股）；v18 起「连续一字涨停且涨停开盘」的个股不属于战法标的（不进机会池与逐笔）；v15 起已纳入「一字涨停买不进不统计」「一字跌停无换手顺延到首个可成交日」两类可成交性约束，v16 起另纳入「冲击空间突破失败（盘中冲板后回落炸板）」买点——该判定基于冲击前已确立的空间压制高度与日K触板，不依赖收盘市场阶段，也不含分时的冲击时点与回落路径；仍不含滑点 / 手续费 / 部分成交量不足等实盘摩擦；「盘中触及 -7%」按当日最低价相对前收判定并以 -7% 价成交，仅供战法统计参考

### 15.1 统一时点与板块效应（三条战法共用）

- **时点**：T 日复盘 → B = T+1 达到条件才买入；页面「当日机会」的日期是**买入日**，其前一交易日为复盘日。
- **买入价**：一律涨停价打板；收盘炸板也按涨停价模拟买入、纳入统计。一字涨停买不进，只进机会池不参与模拟。
- **板块效应（用户口径）**：买入日前一交易日，板块有 **3 板或以上龙头**、且带 **2 板梯队**；该 2 板股在**买入当日赚钱**（收盘涨停或收盘上涨）→ 方向确认，才可参与。不满足则该股不作为机会。

### 15.2 三条战法

| 战法 | 复盘日（T）条件 | 买入日（B）触发 |
|---|---|---|
| 一 空间突破 | 空间龙头板数 **= 空间压制高度**（精确相等，如 5 板 vs 5 板）+ 同板块有板块效应 | 该龙头涨停、冲上压制 +1 板（6 板）→ 涨停价买入 |
| 二 试错龙头 | 市场阶段 = **节点** | 板块内 **3 板以上**、有板块效应、**非一字**的**龙头**（板块最高板）涨停 → 涨停价买入 |
| 三 补涨 | 阶段 = **节点次日**（T−1 为节点）或 **突破 / 主升**；板块有板块效应；**龙头当日一字**买不进 | 买板块**最强次高股**（复盘日板位第二、非一字）涨停 → 涨停价买入 |

卖出沿用统一规则：买入后逐日先判盘中 −7% 止损；收盘仍封涨停继续持有；首个收盘未涨停日尾盘按收盘价卖出；一字跌停无换手顺延至首个可成交日。

### 23.1 刷新为什么一直「更新不了」（真实原因）
实测线上页面：`version.js` 回源请求 **200 正常**、指纹比对逻辑正常，失败点在**实时涨停池**——`api.allorigins.win`、`api.codetabs.com`、`corsproxy.io`、`r.jina.ai` 等公共 CORS 代理在境内全部不可用（超时 / 429 / 401），浏览器跨域直连同花顺被 WAF 拦。于是每次都退回「内嵌收盘池」，用户看到的就是「点了没变化」。
> 结论：**不是数据库问题，也不需要数据库**。数据量只有 15MB 级 JSON，文件即可；缺的是一个**能跑 Python 抓取脚本的后端进程**。静态托管只发文件，浏览器无法让服务器去抓数据。

## 24. v32 本次调整（空间突破只保留三点，其余条件全删）

### 24.1 战法一 · 空间突破（v32 最终口径，只剩三点）

1. **面对空间压制 N 板**（`stages.suppress`，N ≥ 2）；
2. **昨日（T）板块已有助攻股**——该题材昨日梯队中，除今日目标股（昨日 N 板那只）之外，另有 **2 板及以上**的跟风连板股（证明板块在突破前一日已连板成梯队）；
3. **当日出现 N+1 板个股，盘中冲击涨停那一刻即判定突破买点，按涨停价买入**；**随后回落炸板＝突破失败，该笔同样按涨停价买入并纳入统计**；只在突破当日参与，不延到次日。

**本次删除的条件（全部）**：上一空间龙头断板日大长阴 / 断板次日跌停、当日板块赚钱效应榜（≥3 板再涨停 + ≥3 只涨停）、当日梯队助攻校验、`money_effect` 板块验证、高开但不是涨停开盘、连板 ≥3 板起关注、按题材榜限定题材范围。

**保留的只有可成交性口径**（不是选股条件）：一字涨停（集合竞价封死、全天未开板）买不进，只进机会池、不参与模拟；连续一字开盘同样不进逐笔。

**实现变化**：空间突破从「按题材榜遍历」改为**独立按日遍历全市场**——只要当日有 N+1 板个股、其题材昨日有助攻，即触发，不再受当日赚钱效应榜/梯队门槛限制。`board_assist_prev` 改为「排除目标股本身、另有 ≥2 板股」，不再要求「低于当日最高板」（原写法在 N=2 时永远无解）。

## 26. v34 定时抓取重置（16:30 起每半小时轮询，成功即停）

> 对应本次反馈：「重置一下，每天定时抓取淘股吧湖南人复盘数据填充复盘数据，四点半开始，每半小时抓取一次直至提取成功为止」。

### 26.1 旧机制的问题

原来是 16:00 / 17:30 / 19:00 / 21:00 四个固定班次，班次之间是**空窗**：主贴只要落在两个时间点之间（如 17:37 发布），就只能等下一班，而下一班又常被「今日数据已生成」的幂等判断挡掉，最后落到同花顺兜底（`ztpool`）。

### 26.2 新机制：`hunan_poll.py`

平台任务改为**每 30 分钟触发一次**（16:30 → 23:30 共 15 轮），脚本自己决定这一轮要不要干活：

| 状态 | 判定 | 动作 | 耗时 |
|---|---|---|---|
| `done` | `themeSource[今日] ∈ {tgb, weibo}` 且 `themeDetail[今日]` 非空 | 直接退出，不再抓取/重建 | ~0.5 s |
| `waiting` | 淘股吧、微博都还没发收盘复盘 | 只查两个列表页，不重建 | 2~4 s |
| 抓取 | 主贴已发 | 淘股吧正文图 OCR 优先，微博纯文本兜底；两源都抓、取题材更全的一侧（并列用淘股吧） | 首次 OCR 约 1 min，命中 `.ocr_cache.json` 后 2 s |
| 重建 | 题材写入 `.theme_backfill.json` / `.hunan_boards.json` | `update_daily.py --slot 5 --force`（涨停池 + 合并 + 发布） | 2~4 min |
| `waiting` | 文章已发但正文还没有复盘表（如只有「晚间消息汇总」） | 视为未就绪，下一轮再来，不报错 | — |

细节：

- **时段闸门**：`--once` 在 16:30 之前、23:59 之后直接退出（不发请求、不写日志），所以定时任务可以用一条 cron 覆盖整天而不产生请求；
- **周末跳过**：周六日直接退出；
- **幂等**：成功后所有后续轮次都是 0.5 秒退出，不会再重建——这就是「第一次抓到后后面无需执行」；
- **状态文件**：`.hunan_poll.json`（最近一次状态）、`.hunan_poll.log`（append 日志，排查用）。

### 26.3 任务变更

| 操作 | 任务 | Cron |
|---|---|---|
| 删除 | 复盘更新·16:00首抓 | `0 0 16 * * *` |
| 删除 | 复盘更新·17:30重试1 | `0 30 17 * * *` |
| 删除 | 复盘更新·19:00重试2 | `0 0 19 * * *` |
| 删除 | 复盘更新·21:00末次 | `0 0 21 * * *` |
| 新建 #15934031 | 复盘抓取·16:30首轮 | `0 30 16 * * 1-5` |
| 新建 #15934039 | 复盘抓取·17:00-23:30每半小时 | `0 0,30 17-23 * * 1-5` |
| 保留 | 日K刷新·每30分钟 | `0 0,30 9-15 * * 1-5` |

两个新任务的超时都设为 **1800 秒**、重试 1 次（首次 OCR 15 张图 + 重建需要余量）。

`python3 hunan_poll.py --once --force`：

- 淘股吧 `11.18湖南人消息汇总+晚间消息汇总` → 15 张正文图 → OCR 解析出「国产算力 25 只 4 板」（首次 57.5 s，二次 2 s）；

### 26.5 边界

## 27. v34 定时能力搬进应用（自动化任务环境隔离的应对）

> 对应本次反馈：「重置一下，每天定时抓取淘股吧湖南人复盘数据填充复盘数据，四点半开始，每半小时抓取一次直至提取成功为止」。

### 27.1 先做了，然后发现任务根本改不到数据

按需求建了两个任务（`0 30 16 * * 1-5` + `0 0,30 17-23 * * 1-5`），`hunan_poll.py` 也端到端跑通了（见 26 节）。

但 21:29 那轮任务执行完（`lastRunAt=21:29:26`），本地 `.hunan_poll.log` 没有任何新增；再建两个一次性诊断任务（一个 `cd` 后写探针、一个无条件 `touch /workspace/task_probe2.txt`），**全盘 `find / -name task_probe*` 都找不到产物**。

结论：**自动化定时任务跑在独立沙箱里，与站点所在的工作区不共享文件系统**。这也解释了长期以来的怪现象——本站 `.update.log` 从未被创建过，四班固定任务（16:00/17:30/19:00/21:00）其实一直在空转。

### 27.2 方案：把定时器放进站点进程

站点本身是**单端口应用**（`app.py`，由 `publish.js --language python` 发布），所以让应用自己定时最直接——文件读写、构建、对外服务都在同一份磁盘上。

`app.py` 新增后台调度线程（`_sched_loop`）：

| 时段 | 动作 | 说明 |
|---|---|---|
| 工作日 16:30-23:59，每小时 00/30 分 | `hunan_poll.py --once` | 自带幂等与窗口判断，成功后各轮 0.5 秒退出 |
| 进程启动时（窗口内） | 同上，立即补一次 | 沙箱休眠会停线程，唤醒后靠这次「补抓」把漏掉的补上 |
| 工作日 09:25-15:10，每小时 00/30 分 | `refresh_klines.py --recent 12` | 原「日K刷新」任务同样空转，一并搬进来 |

踩到一个坑：`update_daily.py` 构建完会调 `publish.js --language static`，在应用模式下会把线上应用**覆盖回静态托管**。已加 `SKIP_PUBLISH=1` 开关，`hunan_poll.py` 调构建时默认传入；构建产物写盘即生效，不需要再发布。

状态落盘 `.sched_status.json`，并挂在 `GET /api/status` 的 `sched` 字段上——「定时到底跑没跑」看一眼接口就知道。

### 27.3 任务与链接

- 4 个旧的复盘任务 + 2 个新建的复盘任务 + 1 个日K任务**全部删除**，当前自动化任务列表为 0；
- 站点重新发布为 Python 应用，**分享链接不变**：`https://aebe03640c921d2fe.app.workbuddy.host/?sharecode=LERGP4G4UT`；
- 页面「⟳ 刷新」仍走 `POST /api/refresh → refresh_job.py`（抓涨停池 + 重建，不发布），与内置定时共用 `.build.lock`。

### 27.4 实测（2026-11-18 22:00-22:08）

- 应用启动 15 秒后自动补抓：`sched.tail = 今日（20261118）题材已就绪：来源 tgb，3 个题材`；

### 27.5 仍存在的边界

### 29.4 顺带修掉一个隐性 bug：增量刷日K会把分片裁小

`refresh_klines.py` 只拿得到「近 12 个交易日」的需求集，而 `stock_klines.refresh()` 是按需求集
重切 `klines/klines_*.json` 分片的。于是每跑一次盘中刷新，历史股票日的窗口就被裁掉一批，
表现是：`verify_space.py` 用分片独立复算 `boardEarn` 时出现 48 处不一致（数据本身没错，
是分片少了复算需要的 K 线）。

修法（`stock_klines.py`）：先把上一轮分片读进来，本轮写盘时按 `code` **合并保留**——
同一只股票同一日期以新一轮为准（新数据覆盖旧数据），上一轮有、本轮需求集没覆盖到的个股/窗口原样保留。
这样覆盖**只增不减**，盘中增量刷新不会再破坏全期可点性。
